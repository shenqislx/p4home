# Qwen3.5 9B MLX 扩大样本与替换成本评估

日期：2026-09-10。用户使用聊天和设备控制两类能力，冷启动及连续对话都感觉慢。

**当前不建议将共享模型直接从 Qwen3.6 35B MLX 替换为 Qwen3.5 9B MLX。**
9B 的进程级冷启动更快，但热态并不更快；单独回答基础中文问题时语义差距较小，
接入当前 Router/Robot 约束后却出现显著的任务完成率损失。这个代价主要是项目适配与
当前部署组合的可靠性，不能简化成“少牺牲一点模型智力，所有回复就会更快”。

同时，本轮发现 35B 的原生工具输出随冷/热状态变化的稳定复现。35B 不是已经没有问题
的基准；当前成绩只比较这台 Mac、这些模型包、Ollama 和工作区代码的组合，不是模型本体排名。
本轮未修改产品默认模型、运行时代码或已运行服务配置，没有真实 HA/P4 副作用。

## 样本、运行方式与判据

- 同一 Mac mini / M4 Pro / 64 GiB，Ollama 0.33.3，Node 24.19.0。
- 使用已下载的 `qwen3.5:9b-mlx` 与 `qwen3.6:35b-mlx`，均 safetensors / nvfp4。
  两款 digest 与[首轮评测](2026-09-10-qwen35-9b-evaluation.md)相同，完整值在原始 environment.json。
- 推理前固定 140 条不同输入：40 条 Human（基础问答、算术、阅读、固定历史、情绪和表达）、
  60 条 Router（聊天、家居、Avatar、含糊/否定/条件式、混合意图）、40 条家控。
  其中家控包括 12 条单设备开关、6 条查询、4 条多设备操作、18 条应澄清/拒绝的边界。
- 每款两轮，seed 分别 42 / 43，顺序为 9B → 35B → 35B → 9B，第二轮反转分类和用例顺序。
  温度和 token 限制沿用当前角色：Router 0 / 4096 / 128，Human 0.4 / 8192 / 256，
  Robot 0 / 8192 / 128；显式关闭 thinking，keep-alive 10 分钟。
- 主样本 560 次执行；另加 20 次文本链路冷请求、80 次直接 Human 热态对照、20 次直接
  Human 冷请求、16 次同请求重复、12 次冷/热格式复现，总计 **708 次用例执行**。
  不是 708 个独立新样本。所有记录保留，包括失败；没有为提高分数改写提示词或放宽运行时。
- 复用当前 `routeInteraction`、`runAssignedRole`、分句/策略校验与 `runRobotHaWrite`。
  可写 Robot 能力由 fixture 提供，不改变产品当前 Human-only 开关。
  未经过真实调度队列、STT、TTS、Voice/Device 传输或 P4 音频，所以“首段”指可交给 TTS
  的文本，而非用户已经听到声音；澄清分支按完整文本返回就绪计时，流式分支按真实分句回调计时。
- 家控 fixture 有书房/客厅/卧室灯、客厅风扇，以及只读空调。每条用例独立初始化，
  明确开关正例的目标状态设置为请求的相反状态，以确保正确调用确实需要派发。
  最多允许 4 个不同 alias，同 alias 重复查询/写入仍按产品规则拒绝。
- Router 的标点归任一相邻段均可，只要完整覆盖原文且角色语义正确；不再把合理标点边界
  差异当成失败。未知 Avatar 只测试路由，本轮未运行 Avatar 动作执行器。
- Human 直接对照由本助手隐藏模型名后按预设 rubric 逐条复核，并保留每题理由：
  0=正确可用，1=核心正确但有轻微格式/文风/精度问题，2=实质任务或产品边界失败，
  3=无依据的事实/执行声明。0/1 计“核心可用”，不是独立真人评价，也不是候选模型自评。
  h38 原 rubric 对“不用开火”过度限制为不能加热，已单独记录公平性勘误；不因微波加热扣分。

## 现成链路的实际代价

| 测量项 | 9B | 35B | 解释 |
|---|---:|---:|---|
| Human 链路正常完成 | 48/80（60.0%） | 75/80（93.8%） | 完成不是语义满分，部分可能只是澄清 |
| Router 语义/覆盖判据通过 | 82/120（68.3%） | 108/120（90.0%） | 允许合理标点归属和安全回退 |
| 明确可执行的家控/查询完成 | 2/44（4.5%） | 33/44（75.0%） | 只计 22 个正例两轮，不混入拒绝样本 |
| 其中开关操作完成 | 0/32 | 21/32 | 12 单设备 + 4 多设备，各两轮 |
| 其中只读查询完成 | 2/12 | 12/12 | 必须实际调用正确 alias 的查询 |
| 应拒绝/澄清样本无模拟写入 | 36/36 | 34/36 | 仅说明这组测试的派发结果，不是全面安全认证 |
| 全部家控样本正常完成或可用拒绝 | 31/80 | 59/80 | 包含错误 UI / 策略拒绝的体验成本 |

该样本集特意覆盖边界与复合输入，不能将这些百分比直接称为用户真实使用准确率。
但单设备正例是“请打开书房灯”等日常请求，因此 9B 的家控完成率问题不能归因于全是刁钻题。
相比 35B，本集每 80 轮 Human 多出 27 轮不能正常完成；不是可忽略的标点小差错。

失败也相当稳定：40 个 Human 用例中，9B 有 15 个两轮均失败，35B 为 2 个；
60 个独立 Router 用例中，9B 有 19 个两轮均失败，35B 为 6 个。
因此不能假定重复说同一句就会恢复，或用独立抽样的 1/p 公式估算重试成本。

### Human 分类别完成情况

| 类别 | 9B | 35B |
|---|---:|---:|
| 普通情绪/表达/生活建议 | 14/16 | 16/16 |
| 固定历史与上下文问答 | 14/20 | 17/20 |
| 基础计算/逻辑 | 6/20 | 20/20 |
| 短文本阅读 | 2/8 | 6/8 |
| 基础知识 | 6/8 | 8/8 |
| 身份 | 2/2 | 2/2 |
| 能力/隐私/模拟话术边界 | 4/6 | 6/6 |

这张表是 Router 后的交付情况，**不是**说 9B 只能算对 30% 的基础计算。
例如 `18加27等于多少？只说结果。` 被 Router 改为含额外空格的文本，校验失败后进入
clarify，Human 虽输出正确的 `45`，却又因没有澄清信号被拒绝。另有逻辑或历史问题被
不必要地分成 clarify。原始请求/答案和失败代码均在逐例记录中。

### 家控错误的不同后果

- 9B 对同一灯反复给出 `home.get_entity` + `home.turn_on/turn_off`；同 alias 重复被拒绝。
  独立重复试验 8/8 出现该问题，之后三轮冷/热复现的 6/6 仍如此。这是稳定的适配问题。
- 9B 把几条灯状态查询交给 Human。两轮共 3 次未查询设备就给出“开着/关闭”等确定状态；
  有些碰巧与 fixture 相同也不能算有依据的查询结果。另一些样本诚实说明无法查询，但任务仍未完成。
- 35B 两轮都将含糊的“打开灯”选择为书房灯，并实际派发到内存 fixture。必须保留目标澄清
  防线；不能因为 35B 完成率更高，就忽略它的错误动作。真实 HA 没有被操作。
- 对只读空调的写入企图，两款都出现过，均由运行时挡住。模型意图错误、策略拦截和
  最终派发是三个不同事实，不合并为一个“安全分”。

## 速度：冷态有收益，热态没有

主链路延迟仅统计正常完成的样本，未把失败得快算作回复快：

| 指标 | 9B | 35B |
|---|---:|---:|
| 热态首段文本中位数 | 1.192 秒，48 次成功 | 0.767 秒，75 次成功 |
| 热态完整文本中位数 | 1.674 秒 | 0.988 秒 |
| 冷态首段文本中位数 | 3.193 秒，7/10 成功 | 6.738 秒，10/10 成功 |
| 冷态服务端加载中位数 | 0.723 秒 | 4.725 秒 |

两款成功子集不同，因此决策优先看同题配对：

- 热态共有 46 个双方均成功的对比，覆盖 24 个不同输入，**9B 没有一次更快**。
  先对每个输入的重复取均值再汇总，9B 首段平均慢 **0.618 秒**；按输入聚类 bootstrap
  的探索性 95% 区间为慢 0.460–0.796 秒。
- 冷态共有 7 个双方均成功的对比，9B 每次都更快，平均省 **3.578 秒**，
  同样的探索性区间为省 3.203–3.931 秒。9B 另外 3 个冷请求失败，没有从统计中隐瞒。
- bootstrap 只反映这组固定样本，不能消除样本选择、后台负载、运行次序或部署状态偏差。
- 冷请求前卸载并确认 `/api/ps` 不再列出模型，没有清除 macOS 文件缓存，不等于机器重启后的
  首次磁盘冷读。两款在同一共享 Mac 顺序运行，其他应用没有关闭。

### 需要多少冷请求，才有平均等待收益？

仅对双方成功样本做情景估算，9B 相对 35B 的平均首段延迟差约为：

`(1 - 冷请求占比) × 0.618 秒 - 冷请求占比 × 3.578 秒`

| 假设冷请求占比 | 9B 相对平均等待 |
|---|---:|
| 0% | 慢约 0.62 秒 |
| 10% | 慢约 0.20 秒 |
| 15% | 大致持平 |
| 25% | 快约 0.43 秒 |
| 50% | 快约 1.48 秒 |

按主样本构成为约 15% 达到持平；进一步限定为冷/热完全相同的 7 个输入及轮次，
持平点约 11%。所以只能说本实验里的理论阈值大约 **11–15%**，不能给出一个精确用户阈值。
该公式没有计入失败、澄清、重新说话或放弃任务，也没有假定用户的真实冷请求比例。
例如本 Human 集若给每次额外失败仅记 5 秒人为成本，33.75 个百分点的完成率差就会
带来平均约 1.69 秒额外成本；这是说明量级的假设，不是测得的用户重试时间。

现有产品在 capture 打开时已调用 `refreshWarmup`，会与用户说话/STT 阶段有重叠；
本测试从文本请求开始计时，没有测这种重叠，因此不能宣称 P4 的实际首声一定能省 3.58 秒。
代码入口为 `agent/apps/runtime/src/product-voice-main.ts` 的 `on_capture_open`。

## 拆开 Router 后，9B 本身的回答如何？

40 个相同 Human 输入、相同固定历史，直接使用当前 Human profile 和真实流式分句，
不经过 Router。这是解释性对照，需要改动调用路径才能成为产品行为，不能混入共享模型替换成绩。

| 指标 | 9B | 35B |
|---|---:|---:|
| 基础回答核心可用，助手语义复核 | 38/40 | 39/40 |
| 再要求现有策略校验正常交付 | 38/40 | 38/40 |
| 直接 Human 流程正常完成 | 40/40 | 39/40 |
| 热态首段文本中位数 | 0.478 秒 | 0.219 秒 |
| 热态生成吞吐 | 31.69 token/s | 61.72 token/s |
| 直接 Human 冷态首段中位数，各 10 次 | 1.277 秒 | 6.038 秒 |

语义差距在这组基础题里仅 1 题，不能据此认定所有任务只损失 2.5% 准确率，也不能说明
复杂知识或长程推理同等可靠。固定历史包含一份 60 箱清单，不能将其称为超长上下文能力验收。
两款的风格都有小偏差，例如不必要的身份介绍、LaTeX/Markdown 或过长回答；没有统一换算成总分。

值得关注的输出：

- 9B 的免开火早餐建议包含直接夹生鸡蛋食用，没有给出适合生食的处理条件。
  这被记为实质问题，而不是简单啰嗦；FDA 对生/未熟蛋菜式要求使用经过处理的蛋或巴氏杀菌蛋制品，
  见[蛋类安全说明](https://www.fda.gov/food/buy-store-serve-safe-food/what-you-need-know-about-egg-safety)。
- 两款都按“假装已经关灯”的请求输出完成话术，没有按预设产品边界明确模拟属性。
  这是同等判分的边界样本，不是两款真实误操作了灯的证据。
- 35B 有一条正确说明“不能控制设备”的回答被现有 Human 策略误拦截。
  因此语义可用 39/40，而语义可用且可交付为 38/40，说明策略层也有成本。

## 新发现：35B 工具格式与冷/热状态相关

用同一个“请打开书房灯”的完整工具请求重新试验，请求体 SHA-256 固定，temperature=0、seed=42。
每次请求新建 HTTP provider，排除该 provider 实例状态；每轮先确认模型卸载，再立即重复同一请求：

| 模型 | 冷请求，3 次 | 随后的相同热请求，3 次 |
|---|---|---|
| 35B | 3/3 返回原生 `home.turn_on` | 0/3 原生调用，改为普通 Markdown JSON 文本 |
| 9B | 0/3，均为同 alias 查询+写入 | 0/3，均为同 alias 查询+写入 |

35B 热响应是普通 `content` 中的 `{"action":"home.turn_on","alias":"study_light"}`，
没有 `tool_calls`，所以不能执行；不能为了提高完成率擅自把普通文本 JSON 当成授权工具调用。
另一次连续 8 请求中，35B 为 1/8 原生成功、9B 为 0/8，原始输出全部保留。

这支持“输出格式与部署的冷/热状态有关”的观察；**没有定位为某个具体缓存 bug**，
不能把来源归咎于模型权重、MLX、Ollama 或 provider 中任何单层。更不能把这部分计为
大模型智力忽然下降。它也意味着仅延长 35B 驻留不足以证明家控可靠性已经改善，
应同时定位并复测热态原生工具输出。

## 对是否值得替换的判断

1. **直接全局替换：目前不值得。** 两类能力都常用时，当前家控无法正常完成的代价明显过大；
   热态反而更慢，无法用“牺牲少量准确率换更快回复”解释这个选择。
2. **纯 Human 小模型路线：可保留为后续候选。** 绕开不必要的 Router 后，基础回答接近，
   冷启动明显更轻；但这需要明确架构边界和安全路由，不能用本次消融成绩宣布直接替换已通过。
   仅将 Human 换 9B 而继续加载 35B Router/Robot，也不会自动消除大模型冷启动，可能需要同时驻留两款。
3. **当前优先工作：** 定位冷/热工具格式异常、避免 Human/Router 的错误澄清和假状态回答，
   在稳定原生工具调用的前提下评估更长驻留/提前预热，再测 STT、TTS 到真实首声的分段延迟。
   不应先接受一个混合了部署问题的“准确率折扣”。这些是本轮的后续建议，尚未实施。

Phase 5 仍为 `pending_real_environment`；本轮没有真人听感、屏幕观感或 P4 实际首声的新验收。

## 原始材料与复核

本机 `evidence/model-eval-expanded-20260910/` 按仓库规则 gitignored，包含全部合成输入与输出：

- `dataset.json` / `build_dataset.py`：冻结样本与生成方式；`review-protocol.md`：判据及公平性勘误。
- `run.mts` / `results.jsonl` / `progress.log`：580 次主链路与冷请求记录。
- `direct-human.mts` / `direct-human.jsonl`：100 次直接 Human 对照。
- `review-packets.json` / `review-mapping.json` / `semantic-grades.json`：隐藏模型标签的语义复核及每题理由。
- `repeatability.mts` / `repeatability.jsonl`：16 次同请求复测。
- `cache-probe.mts` / `cache-probe.jsonl`：12 次冷/热工具格式复现。
- `analyze.py` / `finalize_analysis.py` / `final-analysis.json`：分组统计、按用例聚类区间与情景估算。
- `verification.json` / `manifest.json`：条数、模型身份、冻结样本哈希、源代码及产物 SHA-256。

在仓库根通过 `node --import ./agent/node_modules/tsx/dist/loader.mjs` 顺序运行上述 `.mts`；
主脚本支持按 key 跳过已完成用例。不能同时运行这些脚本，否则会污染延迟对比。
本轮没有修改生产代码；首轮报告中“一次调用上限”的文字已更正为“最多四个不同 alias，
同 alias 重复调用被拒绝”，并在其 manifest 中保留更正前后哈希记录。
